# architecture
- Derive contextual associations automatically from the navigation flow rather than presenting manual selectors — when a user is already in a specific visit/patient context, auto-associate new records (including consultations) with that existing context instead of creating a new visit or asking them to pick it. Confidence: 0.85
- For CRUD modals, store shared form templates in a partials folder within the page directory and reuse the same template for both create and edit operations. Confidence: 0.85
- When adding edit capability to a sub-entity record, mirror the store path end-to-end: add an Update*Request with the same rules as the Store request, a controller `update()` method, a named PUT route, and reuse the same modal form with an optional record prop that prefills defaults and switches between `router.post`/`router.put` and a 'Record'/'Save' submit label based on whether a record is passed. Confidence: 0.7
- For complex forms with multi-line item tables (e.g., prescriptions with medicine rows), prefer dedicated full pages over modals. Confidence: 0.55
- Within multi-item form pages, prefer accordion-style cards (collapsible, one card per item with header summary and expandable 2-column grid body) over dense horizontal-scrolling item tables. Confidence: 0.50
- For multi-item forms (e.g., prescriptions with medicine rows), prefer a read-only summary table with modal dialogs for individual item add/edit — table for scannable overview, pop-up form for focused detail entry. Confidence: 0.85
- Existing prescription records should remain read-only by default; require an explicit prescription-level Edit action before enabling item changes, while keeping item rows non-editable outside edit mode. Confidence: 0.95
- Patient sub-entities (attachments, medications, prescriptions, surveillance, consultations, paraclinic requests) should be scoped to a specific visit, not just owned by the patient. Confidence: 0.80
- Prescriptions have a one-to-one relationship with visits: each visit has exactly one prescription (use `firstOrCreate` on `visit_id`, not `HasMany`). Confidence: 0.85
- When a separate update endpoint/path exists, keep the `store` action create-only — no delete-then-recreate (upsert) or conditional item-creation guards in `store`; enforce the uniqueness/existence rule via FormRequest validation (e.g., `Rule::unique('prescriptions', 'visit_id')`) so `store` is a plain create. Confidence: 0.80
- For managing visit-scoped sub-entities (like prescriptions), prefer inline tab-based management UI (table + modal for add/edit within the tab) over dedicated create/edit pages. Confidence: 0.75
- Hardcoded option arrays in frontend config (e.g., `MEDICINE_ROUTE`) should become dynamic, DB-backed reference data manageable from a Settings CRUD page — mirror the existing analogous module (e.g., Units) end-to-end: migration + model + controller + Store/Update requests + `settings/<name>` resource route + sidebar entry + settings list page + modal create/edit form, then feed the list to forms via a deferred Inertia prop (value stored in DB, display label rendered in the dropdown, e.g., `code`/`name`). Confidence: 0.8
- When a hardcoded option array is converted to DB-backed reference data, seed the original options (keyed via `firstOrCreate` on the stored value) so existing records remain data-compatible. Confidence: 0.7
- When standardizing component usage or patterns across the project, pick one module (e.g., patients) as the canonical "baseline" and align all other modules to match its conventions, rather than designing a new standard from scratch. Confidence: 0.9
- Place ambient TypeScript declaration files (`.d.ts`) for module types and framework augmentations (e.g., Vite client types, CSS module declarations) in `resources/js/types/`. Confidence: 0.55
- When `import.meta.glob`'s generic parameter causes type compatibility issues with the consuming API (e.g., `createInertiaApp`'s `resolve`), prefer omitting the generic and using an `as` type assertion on the result instead: `import.meta.glob('./pages/**/*.tsx') as Record<string, () => Promise<{ default: PageComponent }>>`. Confidence: 0.50
- When an IDE/static analyzer reports an "internal limitation" on a large controller method (too many inferred inline types, degraded code completion), fix it by extracting each inline data-shaping closure into a small private method that returns a single typed array shape (e.g., `visitPayload()`, `prescriptionPayload()`) and slimming the public method down to assembling them — keeps IDE type inference and code completion intact rather than leaving a type-inference black box. Confidence: 0.55
- Prefer data-driven UI rendering for navigation such as sidebars: keep menu sections, labels, routes, nesting, and icon references in a typed TypeScript configuration module so icons can be imported directly, and render the structure generically rather than hard-coding repeated JSX branches. Confidence: 0.95
- Closing a visit should only transition the current visit to a closed state, never automatically create a replacement; when no active visit remains, show an explicit “Start New Visit” action. Confidence: 0.95
- Delete genuinely dead, broken code (never imported, references undefined variables) rather than patching it to pass lint — verify with grep that nothing imports it and check `git diff` to confirm no substantive work would be lost before removing. Confidence: 0.70
- When registering a Settings CRUD resource under a prefix like `settings/routes`, Laravel names routes by the last URI segment (`routes.*`) and derives the implicit binding param from that segment (`{route}`). If the controller type-hints a differently-named model param (e.g., `MedicationRoute $medicationRoute`), implicit binding silently skips, leaving the model null and causing a 500 on `$model->update()`. Fix by adding `->parameters(['routes' => 'medicationRoute'])` to the resource registration so the URI param matches the controller signature. Confidence: 0.6
- When a frontend page is relocated (e.g., a module moved under `settings/` with modal-based editing), keep the backend controller in sync so the sidebar target renders: update Inertia render paths to the new page location, point store/update/destroy redirects at the new named route (e.g., `settings.categories.index`), and remove controller actions/routes (e.g., `edit`) that no longer have a corresponding frontend page. Confidence: 0.55
- Prefer computing values from related records at display time over persisting them: when a value (e.g., a prescription's diagnosis) can be derived from associated records (e.g., the visit's consultations), do not add a migration/column, model fillable, form request rule, or interface field for it — expose it as a deferred read-only prop and render it instead of adding an editable form field. Confidence: 0.75
- The first argument to `Inertia::render()` must match the page component's path relative to `resources/js/pages` (without the `.tsx` extension) — a mismatch (e.g., rendering `settings/categories/index` while the file actually lives at `pages/categories/index.tsx`) makes Inertia fail to resolve the component and navigation fails silently. When wiring a route/page, verify the render path against the actual page file location and the sibling controllers' render calls. Confidence: 0.6
